# 模组制定规则与开发流程

适用项目：Bonded Companions  
目的：把玩法决定转化为可维护、可验证、不会破坏整合包存档的实现

## 1. 总规则

1. 先解决玩家问题，再增加内容数量。名单准确、物品不丢失、交互不冲突，优先于多做一种装备。
2. 一个行为只有一个事实来源。玩法看 PRD.md，技术看 Tech-Spec.md，配方看 RECIPES.md，长期修正看 MEMORY.md。
3. 用户明确修正高于旧设计。不能为了保留旧代码而偷偷维持旧数值。
4. 未确认的数值必须写成“测试基线”，不能当成不可变设定。
5. 使用 NeoForge、原版数据组件、附件、标签、菜单和能力；只有这些路径确实无法满足时才使用 mixin。
6. 当前只主动维护用户明确点名的 Create、Carry On、Horseman、Modular Golems、Create: Meowchanics 与 Jade 兼容；它们均为软依赖，缺少时本模组仍应启动。其他模组暂不制作专用兼容，真实冲突留到整合测试后单独评估。
7. 不直接修改目标整合包、第三方 JAR 或正式存档。开发和验证只使用工作区及复制实例。
8. 不用“大重构”掩盖单个兼容问题。每次改动只覆盖当前验收目标。
9. 物品与身份安全高于动画完整。遇到关闭页面、卸载或断链竞态时，可以拒绝操作，不能复制或吞物。
10. 空缺需求不自行补写。原对话的第 12 条为空，保持为空。
11. 实际执行顺序、工具准入和探索停止条件以 `DEVELOPMENT-EXECUTION-PLAN.md` 为准。候选工具清单不等于安装或使用授权。
12. 不再用整体完成百分比或总工时猜测驱动开发；只以任务卡状态和验证证据判断进度。
13. 同一时间只允许一个 `IN_PROGRESS` 任务。没有范围、非范围、验收和验证方式的任务不得修改功能代码。

## 2. 文档优先级

出现冲突时按下列顺序处理：

1. 用户最新明确修正。
2. PRD.md 中的已定玩法。
3. Tech-Spec.md 中的安全和兼容边界。
4. RECIPES.md 中的配方与获取。
5. 测试基线、实现便利和开发者偏好。

例子：狐狸重锤曾可能被解释为“武器加值乘 0.7”，但用户最新修正是“完整正常伤害乘 0.7”。任何代码、测试、提示或文档都必须采用后者。

## 3. 完成的定义

开始一个功能前先写清楚完成条件。一个功能只有在下列项目全部满足时才算完成：

- 行为符合 PRD 的当前数值与优先级。
- 服务端验证所有改变世界或物品的操作。
- 存档保存/读取、区块卸载、实体死亡和维度变化没有身份或物品丢失。
- 自动测试或可重复的 GameTest 覆盖核心规则。
- 游戏内完成一次代表性手工流程。
- 与上述指定清单中直接相关的可选模组完成最小兼容测试；未点名模组不作为当前功能完成门槛。
- UI 没有文字溢出、错位、不可读提示或看不见的可点击区域。
- 相关文档和 MEMORY.md 同步更新。

“能编译”不是完成，“在纯净环境能运行”也不是完整包兼容完成。

## 4. 标准流程：Specify → Plan → Task → Execute → Verify

### 4.1 Specify：规格

输入：玩家问题、用户修正、目标版本与整合包约束。  
输出：PRD 章节、明确的范围外项目、验收标准。

必须回答：

- 这个功能解决谁的什么问题？
- 它会不会与原版或现有模组争夺同一交互、栏位或进度？
- 哪些行为是已定，哪些只是测试基线？
- 最坏失败结果是数值不平衡，还是丢物、复制、坏档？

退出条件：不存在会改变架构的未决产品问题。

### 4.2 Plan：技术计划

输入：已冻结的小范围规格。  
输出：数据结构、事件/API 边界、兼容策略、风险探针与验证方式。

计划必须先检查：

- 是否能复用原版真实栏位，而非复制数据。
- 是否能用数据组件、附件、标签或能力完成。
- 是否必须发网络请求，以及服务端如何验证。
- 是否存在第三方菜单、AI、渲染或能力冲突。
- 失败后如何恢复玩家物品。

退出条件：高风险未知项已经转化为可单独验证的技术探针。

### 4.3 Task：任务拆分

每个任务保持一个可验证结果，推荐模板：

- 标题：动词 + 用户可见结果。
- 用户价值：为什么值得做。
- 范围：本任务会改什么。
- 非范围：本任务明确不改什么。
- 数据/API 变化：组件、附件、payload、标签或配方。
- 验收标准：可观察、可重复。
- 风险：最可能造成的回归。
- 验证：自动测试、GameTest、手工流程、兼容组合。

一个任务若同时修改名单引擎、五种生物和全部页面，必须继续拆分。

### 4.4 Execute：实现

实现顺序：

1. 先写或固定失败测试/最小复现。
2. 只实现当前任务所需的最小路径。
3. 复用已有 helper 与数据契约。
4. 增加必要的错误恢复和日志。
5. 不顺手重构无关代码，不加入“以后可能需要”的抽象。

修改期间不得：

- 把客户端按键当成权限。
- 按显示名称识别玩家或命名实体。
- 保存原版栏位的第二份镜像物品。
- 在多个物种中复制名单优先级代码。
- 让自动化直接访问伙伴装备。
- 用硬依赖引用可选模组类。
- 为了兼容直接替换整个第三方菜单或 AI。

### 4.5 Verify：验证

由近到远运行：

1. 单元测试与数据生成检查。
2. Gradle 编译、测试、资源验证。
3. GameTest 或固定测试世界。
4. 纯 NeoForge 客户端手工流程。
5. 单个相关兼容模组组合。
6. 目标整合包完整复制实例。

发现失败时先修复根因并重跑同一层，再进入下一层。不能把第一轮失败留给玩家手动发现。

## 5. 开发里程碑

### M0：工程骨架与安全网

交付：

- NeoForge 1.21.1 / Java 21 工程。
- mod metadata、日志、数据生成和测试入口。
- 空模组可在纯净环境及目标整合包复制实例启动。
- 文档中记录实际 Gradle 命令与锁定版本。

门禁：不加入玩法前，先证明环境与 209 模组组合能加载。

### M1：六个技术探针

按 Tech-Spec.md 第 17 节验证：

1. Alt 与 Carry On。
2. 马鞍位驮箱与 Horseman。
3. 实体局部点击。
4. 拴桩与 Create 机械臂的原子交换。
5. 美西螈装桶往返。
6. 狐狸受控武器伤害。

探针只产出结论和最小代码，不顺便做完整功能。任何探针失败都先调整技术设计。

### M2：纵向切片——名单、狼与基础页面

交付一条从输入到存档的完整链路：

- Alt 打开页面。
- 名单册记录、装备、保存、加载。
- 白名单绝对优先。
- 狼四个栏位、收纳袋、带刺项圈。
- 一个原版兼容附魔和一个专属附魔完整跑通。

门禁：这条切片稳定后才复制到其他物种。

### M3：狼与美西螈完整附魔

- 忠卫、追猎、不屈及互斥。
- 润腮、逐流、共生回响。
- 渔夫交易、战利品与装桶保存。
- 数值测试与多人效果不叠加逻辑；即使不发布服务器，也要保证集成服务端权威。

### M4：狐狸系统

- 生鸡肉驯服与原版繁殖保留。
- 狐衔真实主手槽。
- 普通武器 D × 0.5、重锤 D × 0.7、移速 × 0.7。
- 衔月刃四种材料和三种专属附魔。
- 青金护符四种附魔及归魂获取。
- 工具只叼取、不破坏方块。

门禁：用固定目标和无甲/有甲两套输入验证每个伤害公式，不靠肉眼估算。

### M5：傀儡

- 控制核心、五档范围、三种模式。
- 名单保留与越界返回。
- 雪傀儡与铁傀儡各自四级、互不通用的装甲补强。
- 铁傀儡减伤附魔和雪傀儡火/冰雪球。
- 与 Modular Golems 同时加载，不增强其自定义实体。

### M6：货运纵向切片

先只实现马用驮箱和货运拴桩：

- 18 格、占鞍位、不可骑。
- 只点上背开仓。
- 内容随物品保存。
- 漏斗与 Create 交换。
- 断链/拆箱/死亡竞态无复制。

稳定后再增加驴、骡、骆驼和炽足兽货具。这样可把库存安全问题修一次，而不是五次。

### M7：山羊、海豚、炽足兽与嗅探兽

按物种逐个完成，不共享不合适的战斗模板：

- 山羊：安全冲撞。
- 海豚：水域可达、缺氧上浮和协猎。
- 炽足兽：热力皮夹、避湿、热行岩浆翻倍。
- 嗅探兽：非战斗模式和种子袋。

### M8：内容、视觉与整合包冻结

- 全部配方、附魔获取、交易、战利品与中文文本。
- 所有装备模型和命中区域对齐。
- 完整兼容矩阵、性能场景和存档迁移测试。
- 平衡数值从“测试基线”升级为“冻结”，或记录仍需观察的项目。

## 6. 代码规则

### 6.1 结构

- Java 21，匹配 NeoForge MDK 风格。
- 类保持单一职责；通用规则以小型服务/纯函数表达。
- 物种差异通过窄适配器组合，不建立多层自定义实体继承树。
- 公共数据契约有 Javadoc；注释解释“为什么”，不复述代码。
- 注册 ID、属性 modifier ID 和网络 payload ID 集中定义并保持稳定。

### 6.2 数据与状态

- 可携带库存放在 ItemStack 数据组件中。
- 实体关系、模式和冷却放在可序列化附件中。
- 原版已有主人/装备槽以原版为权威。
- 所有 schema 带版本，迁移只能前进，不能静默清空未知字段。
- 任何容量变化都必须有溢出恢复策略。

### 6.3 网络与信任边界

- 客户端只能请求，不能决定。
- 每个写操作验证玩家、所有者、实体、距离、菜单会话、槽类型、数量和值域。
- 限制请求频率和名单长度。
- 不在日志打印完整玩家数据、存档内容或本机路径。

### 6.4 Mixin 准入

使用 mixin 前必须在 Tech-Spec.md 记录：

1. 目标功能。
2. 已尝试且不可行的事件/API/能力/Access Transformer 路径。
3. 精确目标方法和版本。
4. 第三方缺失或升级时的失败方式。
5. 对应回归测试。

没有这五项，不接受 mixin。一个兼容点不能演化成“替换整个菜单”。

### 6.5 可选依赖

- compat 包中的类只能在对应 mod id 存在时加载。
- 公共核心代码不引用可选模组类型。
- 缺少兼容模组时不报错、不显示无效设置。
- 兼容失败默认关闭该小功能，不阻止世界加载。

## 7. 玩法与数值规则

- 所有百分比明确是加法、乘法还是对“剩余伤害”生效。
- 不在中间步骤取整；测试使用允许的浮点误差。
- 附魔效果必须写出触发条件、范围、持续时间、冷却、叠加、冲突与失效条件。
- 致命保护冷却记录在实体上，禁止换装绕过。
- 白名单必须覆盖伤害、反伤、投射物、范围效果与复仇目标。
- 新增默认黑名单实体先评估路径能力和灾难风险；监守者、凋灵、末影龙不能仅因实现敌对接口就自动加入。
- 测试基线调整时一次只改一个维度，记录前后场景，避免凭感觉同时改伤害、速度和冷却。

## 8. UI 与视觉流程

1. 先固定每个物种的栏位、容量、按钮和错误状态。
2. 画静态线框并用固定物品填满，检查中文名称是否溢出。
3. 实现静态页面和槽验证，再接实体真实数据。
4. 为正常、空槽、非法物品、袋满、无权限、实体死亡六种状态截图验证。
5. 添加模型后，把模型可见区域与服务器局部命中区域逐一对照。
6. 最后再做动画、粒子和音效，不让表现层阻塞库存安全。

页面必须明确显示：

- 当前主人、模式和名单是否启用。
- 马用驮箱导致“不可骑乘”。
- 忠卫/不屈等非法冲突。
- 拴桩未连接、距离过远、被骑乘、红石锁定等状态。
- 苦力怕主动近战风险。

## 9. 验证规则

### 9.1 修复 Bug

能复现时先建立失败测试或固定复现步骤，再修根因。修复后至少验证：

- 原失败场景。
- 相邻正常场景。
- 保存并重载后的同一场景。
- 直接相关的兼容模组组合。

### 9.2 物品安全专项

每个带物品的功能都要模拟：

- 玩家快速移动物品时关闭页面。
- 生物同 tick 死亡或卸载。
- 货具被拆下时漏斗同时抽取。
- 牵绳断开时 Create 机械臂执行。
- 存档在冷却或移动中保存。
- 旧版本容量与非法槽数据。

允许操作失败并返还原物，不允许出现重复或静默丢失。

### 9.3 性能专项

- 1、20、100 只名单伙伴的错峰扫描。
- 20 个已连接和 20 个未连接拴桩。
- 大量模组实体候选的黑名单查询。
- 等待状态和无名单状态应接近零扫描开销。

## 10. 版本与变更管理

私用阶段仍使用版本号：

- 0.1.x：核心原型，可破坏但必须记录迁移风险。
- 0.2.x–0.8.x：按里程碑增加模块。
- 0.9.x：内容冻结，只修 bug、兼容和数值。
- 1.0.0：所有 v1 验收标准通过。

每次行为变更：

1. 在 PRD 更新用户可见规则。
2. 在 Tech-Spec 更新数据/API 或兼容影响。
3. 配方变化同步 RECIPES。
4. 长期决定和踩坑写入 MEMORY。
5. 增加或修改测试。
6. 在变更记录中写“玩家会感觉到什么”，而不只列文件。

不发布不代表可以不做迁移；私用存档同样可能投入几十小时。

## 11. 构建与安装流程

工程建立后固定为：

1. 使用仓库内 Gradle Wrapper 构建，不依赖全局 Gradle。
2. 运行测试与数据生成验证。
3. 生成带版本的 JAR，记录构建来源和当前提交。
4. 复制目标整合包实例和测试存档。
5. 只把 JAR 放入复制实例的 mods 目录。
6. 先新建测试世界，再载入复制存档。
7. 验证后保留日志、崩溃报告和复现步骤。

在开发脚手架创建之前，不虚构具体 Gradle 任务名；脚手架完成后把实际可运行命令补进 AGENTS.md 与 README.md。

## 12. 发布候选检查表

- [ ] PRD 的 v1 验收标准全部有测试证据。
- [ ] 所有“测试基线”已冻结或明确保留为可调项。
- [ ] 纯 NeoForge 与完整整合包都能启动。
- [ ] Carry On 的 Shift + 右击未被占用。
- [ ] Horseman 栓绳位和原页面未被替换。
- [ ] Create 全部指定物流部件能通过拴桩交换。
- [ ] Modular Golems 自定义实体未被误增强。
- [ ] Create: Meowchanics 猫流程未被注入或绕过。
- [ ] 狐狸重锤为完整 D × 0.7，热行为岩浆中 10% / 20%。
- [ ] 装桶、死亡、卸载、断链和升级无吞物/复制。
- [ ] 中文 UI、物品提示、附魔说明与实际效果一致。
- [ ] MEMORY.md 已记录最终架构、兼容结论和仍有风险。

## 13. 每次交付汇报格式

最终汇报保持简短并包含：

1. 做了什么，以及玩家能看到的结果。
2. 验证了什么，列出通过的测试层级。
3. 未验证或仍有风险的内容。
4. 是否更新了 MEMORY.md。

不要以“应该可以”“理论上没问题”代替验证结果，也不要用询问是否继续作为结尾；下一步明确时直接进入下一项已排定任务。
